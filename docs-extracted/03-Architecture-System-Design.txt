1. System Architecture Overview
The Anti-Hallucination Multi-Agent AI Engineering Audit Platform is built on a four-tier architecture designed to run entirely on Cloudflare edge infrastructure. The tiers are: Ingestion (repository intake and chunking), Agent (multi-agent orchestration and analysis), Enforcement (anti-hallucination guarantees), and Orchestration (lifecycle management and workflow coordination). This architecture was designed specifically for Cloudflare primitives: Workers provide the compute layer, D1 provides relational storage for structured audit data, R2 provides object storage for file chunks, Durable Objects provide stateful agent instances with typed RPC, Workflows provide durable long-running process management, Queues provide asynchronous task distribution, and Browser Run provides headless Chromium for visual testing. The entire system is multi-tenant from the ground up, with tenant_id as the leading column in every database table.
1.1 High-Level Architecture Diagram
The architecture follows a unidirectional data flow pattern. Repositories enter through the Ingestion Worker, which chunks files and stores them in R2. The Coordinator Agent reads the manifest and spawns specialist agents. Each agent claims files, reads chunks from R2, analyzes them using LLM calls via AI Gateway, and writes findings to D1. The Priority Resolver Workflow consolidates findings and computes scores. The dashboard reads from D1 via a separate read replica and streams real-time updates via WebSocket. The Salvation Protocol is triggered by Verification Gate failures and uses external search APIs before producing a Salvation Report stored in D1. Visual QA Agent operates in parallel, using Browser Run to test deployed environments.
1.2 Component Interaction Model
All inter-component communication uses either typed RPC (between Durable Object agents) or D1 queries (for cross-agent awareness). Agents never communicate directly with each other; instead, they share state through the D1 findings table and the shared knowledge ledger. This design eliminates race conditions and circular dependencies. The Coordinator communicates with sub-agents via RPC spawn commands and status polls. Sub-agents communicate with the ingestion layer via R2 read operations and with the enforcement layer via inline Verification Gate calls. The dashboard communicates with the backend via WebSocket for real-time streaming and REST API for on-demand queries. External integrations (GitHub webhooks, CI/CD triggers) connect through the API Gateway Worker.
2. Multi-Agent Orchestration Layer
2.1 Coordinator Agent
The Coordinator Agent is implemented as a Cloudflare Durable Object and serves as the central orchestrator for the entire audit system. It follows a strict principle: the Coordinator never performs code analysis. Its responsibilities are limited to reading the repository manifest from D1, determining which specialist agents to spawn based on detected file domains (for example, if no contracts directory exists, the Smart Contract Agent is not spawned), writing an Agent Registry to D1 with every agent ID, domain, status, and assigned file domains, setting the global audit_run_id UUID that tags every finding in the session, and emitting spawn commands to each sub-agent via typed RPC. The Coordinator also monitors agent status transitions (idle, running, blocked, done), triggers the Priority Resolver Workflow when all agents report done, and handles Salvation Protocol escalations by tracking which findings have exhausted their retry budget. The Coordinator maintains its state in Durable Object storage, which persists across invocations and survives Worker restarts.
2.2 Specialist Sub-Agent Lifecycle
Each specialist agent operates independently through a five-phase lifecycle: CLAIM, READ, ANALYZE, WRITE, and COMPLETE. In the CLAIM phase, the agent queries the claims table for unclaimed files in its domain and inserts a claim record with its agent_id, the file_path, and the current audit_run_id. The claims table has a composite primary key on (agent_id, file_path, audit_run_id, tenant_id), ensuring atomic claim operations that prevent two agents from analyzing the same file. In the READ phase, the agent retrieves the file chunk from R2 using the stored r2_key. In the ANALYZE phase, the agent sends the chunk along with its structured audit prompt to the LLM via AI Gateway, which routes to the configured model provider. In the WRITE phase, the agent parses the LLM response into structured FindingResult objects and submits each through the Verification Gate. Findings that pass all gates are written to the D1 findings table. In the COMPLETE phase, the agent updates its status in the Agent Registry to 'done' and notifies the Coordinator via RPC. If at any point the Verification Gate rejects a finding, the agent enters the Salvation Protocol retry loop.
2.3 ReAct Loop Implementation
Each specialist agent implements the ReAct (Reason, Act, Observe) loop for iterative analysis. In the Reason step, the agent formulates an analysis plan based on the file chunk content and any cross-agent findings it has read from D1. In the Act step, the agent calls tools: readFile to get additional context, queryD1 to check related findings, or searchWeb for external documentation. In the Observe step, the agent processes the tool results and updates its analysis state. This loop continues until the agent has exhausted its analysis plan or reached its token budget. The ReAct loop is bounded by two constraints: a maximum of 5 reasoning iterations per file chunk and a total token budget configurable per-agent in the agent_config table (default 4096 tokens per analysis). These bounds prevent infinite loops and control LLM costs. The agent's reasoning trace (each Reason-Act-Observe cycle) is stored in the audit_logs table for debugging and transparency.
2.4 Cross-Agent Knowledge Sharing
Cross-agent awareness is achieved through a shared knowledge ledger in D1, not through direct agent-to-agent messaging. Every 30 seconds (or upon producing a significant finding), each agent reads the findings table filtered to other agents' work. This enables emergent cross-domain analysis: when the Security Agent finds hardcoded secrets, it writes the finding to D1, and the API Agent reads it during its next awareness cycle, then checks every endpoint for where those credentials might be used. When the Database Agent finds missing indexes, the Performance Agent escalates its own latency findings to higher severity. When the Testing Agent finds no test coverage for a module, it marks all other agents' findings on that module as 'unverified by tests'. This design uses eventual consistency with a 30-second propagation window, which is acceptable for an audit system that operates on the scale of minutes, not milliseconds. The knowledge ledger also prevents agents from duplicating each other's work: if the Architecture Agent has already flagged a circular dependency, the Backend Agent sees this and does not produce a redundant finding.
3. Anti-Hallucination Architecture
3.1 Three Enforcement Layers
The anti-hallucination system operates through three complementary enforcement layers, each at a different granularity level. Layer 1 (Constitutional) operates at the agent level through the CONSTITUTION.md file injected into every agent's system prompt. This layer provides soft enforcement by instructing agents on behavioral constraints. Layer 2 (Verification Gates) operates at the task level through deterministic schema validation that intercepts every agent output before database insertion. This layer provides hard enforcement by rejecting structurally invalid or evidence-deficient findings. Layer 3 (Behavioral Tuning) operates at the configuration level through per-agent LLM parameters (temperature, top_p, max_tokens) that reduce the probability of hallucination at the model generation level. These three layers are complementary: Constitutional Rules reduce the likelihood of hallucination, Verification Gates catch any hallucination that slips through, and Behavioral Tuning lowers the base rate of hallucinatory output. No single layer is sufficient on its own.
3.2 Evidence Verification Pipeline
The Evidence Verification Pipeline is the runtime enforcement mechanism that ensures every finding's evidence_quote is grounded in actual source code. The pipeline consists of three stages. Stage 1 (Schema Check): The Verification Gate validates that evidence_quote exists, is at least 10 characters, and does not contain hallucination-indicative phrases (a configurable blocklist including phrases like 'the code appears to', 'it seems likely', 'probably contains'). Stage 2 (R2 Substring Match): An async Worker retrieves the file chunk from R2 and performs a substring search for the evidence_quote. If the exact quote is not found, fuzzy matching with a Levenshtein distance threshold of 3 is attempted to catch minor formatting differences. Stage 3 (Verdict): If neither exact nor fuzzy match succeeds, the finding is rejected with a specific error code (EVIDENCE_NOT_FOUND) and the agent receives the rejection reason in its next retry prompt. If the match succeeds, the finding is tagged as evidence_verified=true and proceeds to database insertion. This pipeline runs asynchronously to avoid blocking the agent's analysis loop.
3.3 Salvation Protocol Architecture
The Salvation Protocol is implemented as a Cloudflare Workflow with five sequential steps, each with configurable timeouts. Step 1 (Retry 1): The agent receives the Verification Gate rejection and retries with a prompt that includes the specific rejection reason. Step 2 (Retry 2): If Retry 1 fails, the agent retries with a stricter prompt that includes examples of correct evidence extraction. Step 3 (Retry 3): If Retry 2 fails, the agent retries with a minimal-scope prompt that asks only for the single most clear-cut finding. Step 4 (Research Phase): If all three retries fail, the agent uses the searchWeb tool to find external documentation relevant to the code being analyzed. The agent must cite every source with a full URL. Step 5 (Salvation Report): The agent produces a Salvation Report containing all attempted approaches, failure reasons, external sources consulted, and a recommended next action. The report is written to the salvation_reports D1 table and surfaced on the dashboard. The Workflow implementation ensures durability: if the Worker is interrupted at any step, the Workflow resumes from the last completed step.
4. Data Architecture
4.1 D1 Schema Design
The D1 database uses Cloudflare serverless SQLite with 10GB storage per database. The schema follows three design principles: tenant_id is the leading column in every table for multi-tenant isolation and index efficiency; all tables include created_at and updated_at timestamps for audit trail; and the claims table uses a composite primary key to ensure atomic file claiming. Indexes are designed for the primary query patterns: findings by audit_session_id and severity, claims by agent_id and status, and files by audit_session_id and domain_tag. Read-heavy dashboard queries use D1's read replica capability. The schema supports soft deletes: findings are never physically deleted, only status-updated to 'closed' or 'superseded', preserving the complete audit history for regression detection and compliance requirements.
4.2 R2 Storage Architecture
Repository file chunks are stored in R2 using a hierarchical key structure: {tenant_id}/{audit_session_id}/{file_path_hash}/{chunk_index}. Each chunk contains no more than 500 lines of source code. The original file metadata (path, language, line count, domain tag) is stored in the D1 files table, while the actual content lives in R2. This separation allows the D1 queries to remain fast and small while R2 handles the large blob storage. Chunks are stored as plain text with UTF-8 encoding. The content_hash field in the files table (SHA-256 of the full file content) enables change detection for continuous audit: on re-audit, if the content_hash matches, the file is skipped; if it differs, the file is re-chunked and re-analyzed. R2 lifecycle rules can be configured to archive chunks from completed audit sessions after a configurable retention period.
5. Infrastructure Architecture
5.1 Cloudflare Worker Topology
The platform deploys as a single Cloudflare Worker application with multiple Durable Object classes. The main Worker handles HTTP routing, API authentication, and request dispatching. Durable Object classes include: CoordinatorAgent (the orchestrator), SharedMemoryDO (the cross-agent knowledge ledger), and one Durable Object class per specialist agent type (15 classes total). Each Durable Object instance is identified by a unique ID derived from the tenant_id and audit_session_id, ensuring that each audit session gets its own isolated Coordinator instance. Worker CPU limits are set to the maximum 300 seconds for long-running agent analysis, leveraging the fact that LLM inference time (I/O) does not count against CPU limits. The Queue consumer processes up to 10 messages per batch with 3 retry attempts for transient failures.
5.2 Durable Object State Management
Each Durable Object uses Cloudflare's built-in SQLite storage for persistent state. The Coordinator stores its agent registry, audit session status, and workflow trigger state. Each specialist agent stores its analysis state, current ReAct loop position, and token usage counter. The SharedMemoryDO stores the cross-agent knowledge ledger as a series of key-value entries keyed by (file_path, agent_id). Durable Objects hibernate when idle (no requests for 30 seconds) and wake on demand, costing nothing when inactive. This is critical for cost efficiency: with potentially thousands of audit sessions, most agents will be idle most of the time. The Durable Object storage limit of 10GB per instance is sufficient for the agent registry and analysis state, which are structured data measured in kilobytes, not the file content itself.
5.3 Workflow Integration
Cloudflare Workflows handle three long-running processes: the Continuous Audit Lifecycle, the Deterministic Priority Resolver, and the Salvation Protocol. Workflows provide durable execution with automatic checkpointing: if a Worker is interrupted, the Workflow resumes from the last checkpoint. The Continuous Audit Lifecycle Workflow monitors for file changes (via content_hash comparison), triggers re-analysis of changed files, and recalculates the Production Readiness Score. The Deterministic Priority Resolver Workflow loads all findings for an audit_run_id and computes composite priority scores using a deterministic formula (severity weight + category weight + evidence strength + cross-agent correlation), entirely in code without any LLM involvement. The Salvation Protocol Workflow manages the 3-strike retry loop, Research Phase, and Salvation Report generation as described in Section 3.3.
6. Security Architecture
Security is implemented at four layers: authentication, authorization, data isolation, and secrets handling. Authentication uses Bearer tokens issued per tenant with JWT-signed claims including tenant_id, plan level, and expiration. Authorization is enforced at the API Gateway Worker, which validates the token and injects the tenant_id into the request context for all downstream operations. Data isolation is guaranteed by database-level enforcement: every D1 query includes a WHERE tenant_id = ? clause, and the claims table uses tenant_id as a leading primary key column, making cross-tenant data access impossible at the database level even if application code has a bug. Secrets detected by the Security Agent are redacted using SHA-256 hashing: the actual secret value is never stored or transmitted; only the hash and detection context are preserved. Rate limiting at 100 requests per minute per tenant prevents abuse. All agent code execution occurs within V8 isolates with no filesystem access and no network access except to explicitly allowed endpoints (AI Gateway, R2, D1).
7. Real-Time Dashboard Architecture
The real-time dashboard is served as a Cloudflare Pages application backed by Workers API routes. The dashboard connects to the platform via a WebSocket endpoint (/ws/audit/:id) that streams three event types: finding.created (new finding with full details), agent.status_changed (agent lifecycle transitions), and score.updated (Production Readiness Score changes). The WebSocket is implemented as a Durable Object that maintains a fan-out list of connected clients and broadcasts events from the audit pipeline. Historical data (past findings, past audit sessions) is served through REST API endpoints backed by D1 read replicas. The dashboard displays: a Kanban board of findings grouped by severity, a live agent activity log showing each agent's current phase, file-level analysis progress, the Production Readiness Score as a percentage with trend over time, and Salvation Report details for any escalated findings. The frontend uses server-sent events for efficient real-time updates with automatic reconnection on disconnect.
