1. Abstract
This RFC specifies the technical architecture for an Anti-Hallucination Multi-Agent AI Engineering Audit Platform built entirely on Cloudflare edge infrastructure. The platform employs a Coordinator Agent and 15 specialist sub-agents orchestrated through a ReAct (Reason, Act, Observe) loop to perform continuous, evidence-based code audits. Every finding produced by any agent must include a verbatim evidence quote from the analyzed source file, enforced by a multi-layered anti-hallucination system comprising Constitutional Rules, Verification Gates, and Behavioral Tuning. The platform stores audit findings in Cloudflare D1 (SQLite), repository file chunks in R2, and coordinates agents via Durable Objects with typed RPC. Continuous audit lifecycle management is handled by Cloudflare Workflows, ensuring that audits run, re-run on file changes, and track resolution until a quantified Production Readiness Score reaches the target threshold. The Salvation Protocol provides a structured escalation path when agents encounter problems they cannot solve, involving three retry attempts, a dedicated Research Phase with web search, and a final Salvation Report with cited external URLs. A Visual QA Agent leverages Cloudflare Browser Run to perform headless Chromium testing of deployed or staged environments, catching issues that static analysis alone cannot detect.
2. Motivation and Background
Software engineering teams currently rely on two categories of tools for code quality assurance, neither of which is sufficient for modern full-stack applications deployed on cloud-native infrastructure. Deterministic static analysis tools such as ESLint, SonarQube, Bandit, and Hadolint excel at catching syntactic errors, known vulnerability patterns, and style violations, but they fundamentally cannot reason about semantic correctness, architectural coherence, or business logic flaws. They produce high volumes of low-signal noise while entirely missing critical issues such as a missing authentication check on a newly added API endpoint, a race condition in a concurrent data pipeline, or a database query that silently fails to return results for an edge-case input combination. Human code review, while capable of semantic reasoning, does not scale to the velocity of modern development teams and is subject to fatigue, inconsistency, and the reviewer's individual expertise gaps.
Large language models offer a third path: semantic code analysis that can reason about intent, context, and cross-file dependencies. However, LLMs are prone to hallucination, fabricating code paths that do not exist, inventing function signatures that were never defined, and generating findings that sound plausible but have no basis in the actual codebase. The fundamental challenge this platform addresses is how to harness the semantic reasoning power of LLMs while completely eliminating hallucination through architectural constraints rather than prompt engineering alone. The platform achieves this through three enforcement layers operating at different granularity levels, combined with a continuous lifecycle that treats each audit as a living process rather than a one-time scan. The choice of Cloudflare edge infrastructure is driven by the need for low-latency global access, sub-second cold starts via Durable Objects, and a unified platform that provides compute (Workers), storage (D1, R2), orchestration (Workflows, Queues), and browser automation (Browser Run) without vendor fragmentation.
3. Technical Design Overview
The platform follows a layered architecture with four principal tiers. The Ingestion Tier handles repository intake, chunking files into segments of no more than 500 lines, storing them in R2, and writing file metadata to D1. The Agent Tier consists of a single Coordinator Agent (implemented as a Durable Object) and 15 specialist sub-agents (each a Durable Object sub-agent with its own SQLite storage and typed RPC interface). The Enforcement Tier implements the Three Enforcement Layers: Constitutional Rules defined in a CONSTITUTION.md file injected into every agent's system prompt, Verification Gates that perform deterministic JSON schema validation on every agent output before it is accepted, and Behavioral Tuning parameters that control per-agent temperature, top-p, and evidence citation requirements. The Orchestration Tier uses Cloudflare Workflows for long-running processes such as the continuous audit lifecycle, the Deterministic Priority Resolver (a Workflow, not an LLM call), and the Salvation Protocol escalation sequence.
The Coordinator Agent never performs analysis itself. Its sole responsibilities are reading the repository manifest, deciding which specialist agents to spawn based on detected file domains, writing an Agent Registry to D1, emitting spawn commands via typed RPC, tracking agent status transitions, and triggering cross-phase workflows. Each specialist agent operates independently in parallel, claiming files from a shared D1 claims table to prevent duplicate analysis. The claims table uses a composite unique constraint on (agent_id, file_path, audit_run_id) to guarantee atomicity. When an agent encounters a finding it cannot resolve after three attempts, the Salvation Protocol fires automatically, triggering a Research Phase where the agent performs targeted web searches via an external search API, then produces a Salvation Report containing every approach tried, external sources consulted with full URLs, and a recommended next step for the human developer.

The following eight D1 tables form the persistent data layer for the platform. All tables include a tenant_id leading column for multi-tenant isolation, created_at/updated_at timestamps for audit trail, and appropriate indexes for query performance. The D1 database uses Cloudflare's serverless SQLite with a 10GB per-database limit and supports read replication for dashboard queries.

4.3 Agent Prompt Templates
Each agent receives a structured system prompt containing the constitutional rules, role-specific instructions, available tools, and the required output JSON schema. The following templates show the core prompt structure for the Coordinator Agent and two representative specialist agents. All prompts are stored as versioned strings in the agent_config table and can be updated per-tenant without deployment.
Coordinator Agent System Prompt
SYSTEM PROMPT: You are the Coordinator Agent for an anti-hallucination code audit platform. You NEVER analyze code yourself. Your responsibilities are: (1) Read the repository manifest from D1. (2) Determine which specialist agents to spawn based on detected file domains. (3) Write an Agent Registry entry to D1 for each agent. (4) Emit typed RPC spawn commands to each sub-agent. (5) Track agent status transitions: idle, running, blocked, done. (6) Trigger the Priority Resolver Workflow when all agents report done. (7) Monitor for Salvation Protocol escalations. CONSTITUTIONAL RULES: You must not fabricate agent capabilities. You must not invent file paths. You must not assume analysis results. Every decision must reference data from D1 or R2. TOOLS: queryD1(sql, params), spawnAgent(agentId, domain), getStatus(agentId), triggerWorkflow(workflowId, payload). OUTPUT: Structured JSON matching the CoordinatorDecision schema.
Security Agent System Prompt
SYSTEM PROMPT: You are the Security Agent specializing in vulnerability detection, authentication analysis, authorization checks, input validation, secrets detection, and dependency vulnerability assessment. CONSTITUTIONAL RULES: (1) Every finding MUST include an evidence_quote that is a VERBATIM excerpt from the analyzed file. (2) You must NEVER claim a vulnerability exists without quoting the exact code. (3) If you cannot determine whether code is vulnerable, you MUST label it as 'needs-investigation' with severity 'info'. (4) Hardcoded secrets must be flagged even if they appear in test files. (5) You must redact actual secret values in evidence quotes, replacing them with [REDACTED-HASH:sha256hash]. TOOLS: readFile(path), queryD1(sql, params), claimFile(path), writeFinding(finding), searchWeb(query). OUTPUT: Array of FindingResult objects matching the JSON schema.
Performance Agent System Prompt
SYSTEM PROMPT: You are the Performance Agent specializing in database query optimization, N+1 query detection, memory leak identification, caching strategy assessment, bundle size analysis, and CDN/edge optimization opportunities. CONSTITUTIONAL RULES: (1) Every finding MUST include an evidence_quote from the actual file. (2) Performance claims MUST reference specific code patterns, not general advice. (3) You must NOT hallucinate metrics or benchmark results. (4) If you lack execution context, state 'Cannot measure actual performance without runtime data' and downgrade to 'info'. (5) Database findings must reference the exact query or ORM call, not a generalized description. TOOLS: readFile(path), queryD1(sql, params), claimFile(path), writeFinding(finding). 4.6 Anti-Hallucination Enforcement
4.6.1 Evidence Mandate
The Evidence Mandate is the foundational anti-hallucination mechanism. Every finding produced by any agent must include an evidence_quote field containing a verbatim excerpt from the analyzed source file. The Verification Gate validates this field at the schema level: the evidence_quote must be at least 10 characters long, must not contain phrases like 'the code appears to' or 'it seems that', and must be verifiable against the stored file chunk in R2. During the audit, a post-processing step compares each evidence_quote against the actual file content stored in R2 using substring matching. If the quote cannot be found in the source file, the finding is automatically rejected and the agent is forced to retry with a stricter prompt that emphasizes verbatim extraction. This mechanism eliminates the most common form of LLM hallucination in code analysis: fabricating plausible-sounding but non-existent code snippets.
4.6.2 Constitutional Rules (CONSTITUTION.md)
The CONSTITUTION.md file defines absolute behavioral constraints injected into every agent's system prompt. These rules are non-negotiable and cannot be overridden by agent-level configuration. The core constitutional rules are: (1) Never assume code exists; reference only files confirmed in the repository manifest. (2) Never invent function signatures, API endpoints, or database schemas. (3) Never fabricate evidence quotes; all evidence must be extracted verbatim from source files. (4) Never infer implementation details without explicit evidence. (5) Always label unknowns explicitly as 'Unknown: cannot determine from available evidence'. (6) Never produce people-pleasing output; prioritize accuracy over completeness. (7) Never escalate severity to make findings appear more important than evidence supports. (8) Always cite the specific file path and line range for every claim. These rules are enforced at three levels: the agent's system prompt (soft enforcement via instruction), the Verification Gate (hard enforcement via schema validation), and post-processing evidence verification (runtime enforcement via R2 substring matching).
4.6.3 Verification Gates
Verification Gates are deterministic, schema-based validation checkpoints that intercept every agent output before it enters the findings database. Unlike LLM-based evaluation, Verification Gates use pure code logic to validate structural integrity and content constraints. Each gate enforces specific rules: the Schema Gate validates that the output matches the FindingResult JSON schema exactly, rejecting any extra or missing fields. The Evidence Gate validates that evidence_quote is a non-empty string of at least 10 characters and triggers an async R2 substring check to verify the quote exists in the source file. The Severity Gate ensures that critical and high severity findings have evidence quotes longer than 50 characters and impact descriptions longer than 30 characters, preventing agents from slapping high-severity labels on vague findings. The Cross-Reference Gate checks that the file_path in the finding exists in the files table for the current audit session. If any gate fails, the finding is rejected and the agent receives the specific rejection reason along with a retry prompt.
4.6.4 Behavioral Tuning
Behavioral Tuning provides per-agent, per-tenant control over LLM generation parameters to minimize hallucination risk while maintaining analytical capability. Each agent has configurable parameters stored in the agent_config table: temperature (default 0.1, range 0.0 to 0.3 for analysis agents; higher values are locked for non-analysis use cases), top_p (default 0.85, range 0.7 to 0.95), max_tokens (default 4096, range 1024 to 16384), evidence_required (boolean, default true; when true, outputs without evidence_quote are auto-rejected), and max_retries (default 3; number of attempts before Salvation Protocol fires). The tenant configuration endpoint allows engineering managers to tighten or loosen these parameters based on observed agent performance. For example, if the Security Agent produces too many false positives, the tenant can lower its temperature to 0.05 and increase the evidence_quote minimum length requirement.
4.7 Salvation Protocol Specification
The Salvation Protocol is a structured escalation mechanism that activates when an agent fails to produce a valid, evidence-backed finding after three consecutive attempts. The protocol consists of three phases. Phase 1 (Retry Loop): The agent receives the Verification Gate rejection reason and retries with a modified prompt that explicitly addresses the failure. This repeats up to three times with progressively stricter constraints. Phase 2 (Research Phase): If all three retries fail, the agent enters a Research Phase where it uses the searchWeb tool to find external documentation, Stack Overflow answers, or vendor documentation relevant to the code being analyzed. The agent must cite every external source with a full URL. Phase 3 (Salvation Report): The agent produces a Salvation Report documenting every approach tried, the specific failure at each step, all external sources consulted, and a recommended next action for the human developer. The Salvation Report is stored in the salvation_reports D1 table and surfaced on the dashboard with full transparency.

5. Backwards Compatibility
This platform is a greenfield implementation with no legacy dependencies. However, the API versioning strategy uses URL path versioning (/api/v1/) to allow future breaking changes without disrupting existing integrations. All D1 table schemas include a schema_version column for potential future migrations. The agent prompt templates are versioned and stored in the database, allowing rollbacks without code deployment. The Cloudflare Workers compatibility_date is pinned, ensuring runtime behavior remains consistent across deployments. Any future schema migrations will use D1's native migration system with versioned SQL files applied sequentially.
6. Security Considerations
Security is implemented at multiple layers. Multi-tenant isolation is enforced at the database level: every D1 query includes a tenant_id filter, and the claims table uses tenant_id as a leading column in its primary key to prevent cross-tenant data leakage. Authentication uses Bearer tokens issued per tenant with configurable expiration. Secrets detected by the Security Agent are redacted in all outputs using SHA-256 hashing: the original secret value is never stored or transmitted; only its hash and the detection context are preserved. This ensures that even if the findings database is compromised, no actual secrets are exposed. Rate limiting at 100 requests per minute per tenant prevents abuse. The Worker CPU limit of 300 seconds prevents infinite loops. All agent code execution occurs within Cloudflare's V8 isolate sandbox, which provides memory isolation and no filesystem access. The Visual QA Agent's browser sessions run in Cloudflare Browser Run's managed Chromium instances, which are destroyed after each session.
7. Testing Strategy
Testing operates at four levels. Unit tests verify individual Verification Gate functions, evidence quote extraction, and priority score calculation using mock data. Integration tests validate the full agent lifecycle: claim file, read chunk, analyze, write finding, with a real D1 database and R2 bucket in a Cloudflare test environment. Contract tests validate that every API endpoint matches its specified request/response schema using an OpenAPI-derived test suite. End-to-end tests run the full audit lifecycle against a known test repository with pre-characterized expected findings, measuring recall (percentage of known issues detected) and precision (percentage of findings that are valid). The end-to-end test suite includes a hallucination detection component: it intentionally includes files with subtle non-issues and verifies that the agents do not produce false positive findings. Target coverage thresholds are 95% unit test coverage, 100% API contract coverage, and 90% end-to-end recall on the test repository.
