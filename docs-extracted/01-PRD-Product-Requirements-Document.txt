Executive Summary
This Product Requirements Document (PRD) defines the specifications for an Anti-Hallucination Multi-Agent AI Engineering Audit Platform. The platform leverages a Coordinator Agent and 15 specialist sub-agents running on Cloudflare's edge infrastructure to perform continuous, evidence-based code audits on software repositories. Unlike conventional static analysis tools that rely on pattern matching, this system employs large language models (LLMs) orchestrated through a ReAct (Reason, Act, Observe) loop to perform deep semantic analysis of code, identifying architectural flaws, security vulnerabilities, performance bottlenecks, and missing test coverage that deterministic tools routinely miss.
The platform is built entirely on Cloudflare's open-source stack, leveraging Workers for serverless compute, D1 (SQLite) for structured relational data storage, R2 as an S3-compatible object store for file chunk storage, Durable Objects for stateful agent instances with typed RPC communication, Cloudflare Workflows for durable long-running orchestration processes that survive interruptions, Queues for asynchronous fan-out of agent spawn commands, and Browser Run for headless Chromium-based visual QA testing. This edge-native architecture delivers sub-100ms API response times, automatic horizontal scaling across Cloudflare's global network of over 300 data centers, and zero cold-start friction through Durable Object hibernation where agents wake on demand and cost nothing when idle. Every agent's output is governed by a Three-Layer Anti-Hallucination Enforcement system consisting of Constitutional Rules with a CONSTITUTION.md file hard-injected per agent before every analysis turn, Verification Gates implementing deterministic schema validation before any finding is accepted into the findings database, and Behavioral Tuning through dashboard-controlled dials that allow per-agent customization of audit strictness.
The system introduces the Salvation Protocol as a critical safety mechanism, implementing a three-strike escalation path that prevents specialist agents from silently failing on intractable findings or entering infinite retry loops that waste token budget. After three consecutive failed fix attempts on the same finding, the agent automatically transitions into a structured Research Phase, querying authoritative external sources including OWASP documentation for security issues, the National Vulnerability Database (NVD) for CVE references, relevant framework GitHub Issues for known runtime errors, and Stack Overflow for implementation patterns and accepted workarounds. The agent then produces a Salvation Report containing cited URLs, every attempted solution with timestamps, and a list of dependent tasks it now blocks. The Visual QA Agent operates independently by running the actual application in a headless Chromium instance via Cloudflare Browser Run, testing every route, form submission, and admin action to catch runtime failures that no static analysis can detect. Multi-tenant isolation is enforced through a tenant_id column on every D1 table, and all discovered secrets are redacted via SHA-256 hashing before storage or display.
Problem Statement
The Core Problem
Software engineering teams face a persistent and escalating challenge that grows more acute with every new service, microservice boundary, and third-party integration added to their systems: ensuring that codebases meet production-grade standards before deployment. Existing tooling falls into two broad categories, both fundamentally insufficient for modern full-stack applications that span frontend frameworks, backend APIs, database layers, infrastructure-as-code, and third-party service integrations. Deterministic static analysis tools such as ESLint, SonarQube, Bandit, and Hadolint excel at catching syntactic errors, known vulnerability patterns from CVE databases, and style violations defined in configurable rule sets, but they categorically cannot reason about semantic correctness, architectural coherence across module boundaries, or business logic flaws that violate implicit requirements. They produce high volumes of low-signal noise while completely missing critical issues such as a missing authentication check on a newly added API endpoint, a race condition in a concurrent data pipeline, or a database query that silently fails to return results for an edge-case input combination. The consequence is a pervasive false sense of security: teams believe their codebase has been thoroughly audited when, in reality, the most dangerous and costly classes of defects remain completely undetected by any tool in their pipeline.
On the opposite end of the spectrum, human code reviews are expensive, inconsistent, and fundamentally do not scale with the size and complexity of modern software systems. A senior engineer conducting a thorough architectural review of a 50,000-line codebase may spend weeks poring over files and still miss critical issues that fall outside their specific domain expertise. A frontend specialist reviewing a pull request will not catch a subtle database N+1 query problem hidden in a data access layer; a backend engineer performing security review will not notice an inaccessible color contrast violation that makes the application non-compliant with WCAG accessibility standards. The human review process is further degraded by reviewer fatigue after reading dozens of files, time pressure from sprint deadlines that encourage shallow rubber-stamping, and the cognitive impossibility of holding an entire monorepo's dependency graph, API surface, and data flow in working memory simultaneously. Organizations are thus caught between tools that are fast but shallow and humans that are deep but slow, with no existing middle ground that delivers both the semantic depth of expert human review and the operational throughput of automated tooling at a cost that makes economic sense for engineering teams of all sizes.
Why Current Tools Fail
Existing solutions fail along three critical dimensions. First, they lack semantic understanding. A linter can verify that a function is called, but it cannot determine whether calling it in this particular context produces the correct business outcome. A type checker can confirm that a function accepts a string, but it cannot flag that the string is being used as an SQL query fragment without parameterization. Second, current tools operate in isolation. SonarQube does not talk to your test runner; ESLint does not consult your API documentation; your security scanner does not know which endpoints are publicly exposed versus admin-protected. This siloed approach means that a vulnerability involving the intersection of authentication, database access, and frontend routing will never be flagged by any single tool. Third, existing tools produce findings, not solutions. They generate lists of problems but provide no mechanism for prioritization, no understanding of which issues block other issues, and no continuous verification loop that confirms a fix actually resolved the root cause rather than merely suppressing the warning.
The Agent-Based Opportunity
Large language models, when properly constrained and orchestrated, offer a fundamentally different approach. Unlike pattern matchers, LLMs can reason about code semantics, trace data flows across module boundaries, evaluate whether business logic aligns with documented requirements, and identify architectural anti-patterns that emerge only at the system level. A multi-agent architecture, where specialized agents each focus on a distinct domain (security, performance, API design, database schema, frontend accessibility, and so on), can replicate the collective expertise of an entire engineering team. The key innovation is the coordination layer: a Coordinator Agent that orchestrates the specialist agents through a ReAct loop, manages file-claim locks via a D1 claims table to prevent duplicate analysis, resolves priority conflicts through a deterministic scoring algorithm implemented as a Cloudflare Workflow (not an LLM), and maintains a shared knowledge graph that enables cross-agent awareness without direct agent-to-agent messaging. This eliminates the hallucination problem that plagues unconstrained LLM outputs by enforcing an Evidence Mandate: every finding must include an exact quoted snippet from the actual source file with line numbers, or the finding is rejected by the Verification Gate and never reaches the task board.
Why Agent-Based
Semantic Depth
Deterministic tools operate at the lexical and syntactic layers of code. They can detect that a variable is unused, that a function signature has changed, or that a known CVE pattern appears in a dependency. However, the most costly engineering defects live at the semantic layer: a payment processing function that correctly calculates tax but applies it to the wrong currency, an authentication middleware that validates the token format but never checks its expiration, or a caching layer that stores responses for public endpoints but inadvertently caches user-specific data. These are not pattern violations; they are logic errors that require understanding what the code is supposed to do versus what it actually does. Each of the 15 specialist sub-agents is designed to reason within its domain with the depth of a senior domain expert, reading not just the immediate function but tracing data flows, checking cross-module contracts, and verifying that the implementation matches the documented intent. The ReAct loop ensures that agents do not jump to conclusions: they reason about what they observe, take action to gather more evidence by reading related files, and then re-evaluate before filing a finding.
Adaptive Analysis
Static analysis tools apply the same rules regardless of project context. They do not know that a particular endpoint is customer-facing and therefore requires stricter input validation, or that a specific module handles financial transactions and must comply with audit logging requirements. The multi-agent system adapts its analysis based on what it discovers during the audit itself. When the Security Agent identifies hardcoded credentials, it writes that finding to the shared D1 findings table. The API Agent, on its next cross-agent awareness cycle, reads that finding and automatically escalates its audit of every endpoint where those credentials might be transmitted. The Database Agent detects missing indexes; the Performance Agent reads that finding and raises its own latency findings to higher severity because it now understands the query cost implications. This adaptive, emergent behavior is impossible with standalone tools and is what gives the multi-agent architecture its decisive advantage over conventional approaches.
Evidence Mandate
The single greatest risk of using LLMs for code audit is hallucination: the model confidently asserts that a function does not exist, that an endpoint is unprotected, or that a variable holds a specific value, when none of these claims are true. The Evidence Mandate eliminates this risk through a combination of structural and behavioral constraints. Structurally, every finding must include an evidence_quote field containing the exact text from the source file, a file field with the precise path, and a line_range field specifying where the evidence was found. Behaviorally, each agent operates under a CONSTITUTION.md that is hard-injected before every analysis turn, banning phrases like 'production ready,' 'looks good,' and 'should work,' and requiring the agent to explicitly label unknowns as unknown rather than inferring an answer. The Verification Gate, implemented as deterministic schema validation code (not an LLM check), rejects any finding that lacks required fields or contains banned phrases. The agent must retry until its output conforms. This three-layer system ensures that no fabricated claim can reach the developer's task board.
Target Personas
DevOps Engineer
The DevOps Engineer is responsible for the operational health of deployment pipelines, infrastructure configuration, and runtime monitoring. They need to know whether a codebase will survive production conditions before it reaches production. Their primary pain points include: deployment failures caused by undetected configuration errors, secrets leaked into version control that trigger compliance violations, performance regressions introduced by well-intentioned refactors, and the absence of structured runbooks for incident response. The DevOps Engineer values automated, continuous auditing that integrates with their CI/CD pipeline and produces actionable outputs. They want a system that can ingest a repository, identify infrastructure-as-code defects, validate Docker and Kubernetes configurations, check environment variable handling, and produce a prioritized task list that maps directly to their sprint backlog. They also need the Visual QA Agent to verify that deployed applications actually function at runtime, not just that their code passes static checks. The platform's ability to continuously re-audit on every commit and automatically detect regressions directly addresses their need for shift-left quality assurance.
Engineering Manager
The Engineering Manager oversees multiple teams and is accountable for delivery velocity, code quality, and technical debt management. Their challenges include: inability to get a unified view of codebase health across teams, difficulty justifying the allocation of engineering hours to technical debt reduction, lack of objective metrics for production readiness, and the political friction of code review disagreements between senior engineers. The platform serves the Engineering Manager by providing a real-time dashboard with a Production Readiness Score (a single percentage recalculated after every verification), a Kanban task board with priority-ranked findings, per-agent activity logs, and a token usage cost breakdown. They can see at a glance how many critical findings remain, which files are most problematic, and whether their team is making progress against the audit. The deterministic Priority Resolver eliminates subjective disagreements about what to fix first, replacing them with a transparent, math-based ranking that accounts for severity, cross-agent agreement, blocking relationships, and test coverage.
CTO / VP of Engineering
The CTO or VP of Engineering is responsible for technology strategy, platform reliability, and organizational engineering standards. They need to ensure that the company's codebase portfolio meets enterprise-grade security, compliance, and reliability standards. Their concerns are strategic: reducing the risk of production incidents caused by preventable defects, establishing auditable evidence trails for compliance requirements (SOC 2, ISO 27001), controlling the cost of AI-powered tooling, and evaluating whether the engineering organization is maturing its practices over time. The platform addresses these needs through multi-tenant isolation with tenant_id on every table, secrets redaction via SHA-256 hashing, a comprehensive token_usage table tracking cost per agent per model per task type, and the Salvation Protocol which provides documented evidence of escalation and research for issues that cannot be automatically resolved. The CTO can review Salvation Reports with cited URLs to understand exactly what was attempted, what external research was conducted, and why human intervention is required, creating a defensible audit trail for stakeholders and regulators.

Jobs to Be Done Framework
Main Job: Continuously Validate Production Readiness
When I am preparing a codebase for production deployment, I want to run a comprehensive, multi-domain audit that covers security, performance, architecture, testing, and accessibility simultaneously, so that I can be confident the codebase meets production-grade standards without manually coordinating five separate tools, three external reviewers, and a security consultant. The current alternatives force me to run ESLint for code quality, then SonarQube for overall health metrics, then OWASP ZAP for security scanning, then a manual accessibility review against WCAG guidelines, then a peer code review for business logic correctness, each producing disconnected reports in different formats that I must mentally synthesize into a coherent picture of overall readiness. This fragmented approach takes days, produces inconsistent results depending on who runs the tools and in what order, and provides no mechanism for continuous monitoring. I want a single system that produces a unified, prioritized task list with evidence-backed findings from every domain, and that continuously monitors the codebase for regressions as my team ships changes, automatically detecting when a previously resolved issue has reappeared.
Supporting Jobs
The platform addresses several supporting jobs that enable the main job. First, the job of understanding what to fix first is served by the deterministic Priority Resolver, which computes a composite score from severity base values, cross-agent agreement multipliers, blocking relationship multipliers, test coverage multipliers, and refactoring conflict discounts. This eliminates subjective prioritization debates and provides a transparent, auditable ranking. Second, the job of verifying that a fix actually works is served by the Verification Agent, which reads only the commit diff and checks whether the original evidence is still present, providing a mechanical, reproducible verification rather than a subjective re-review. Third, the job of handling intractable problems is served by the Salvation Protocol, which automatically escalates to external research and produces a structured report with cited URLs, saving the developer hours of manual investigation. Fourth, the job of catching runtime failures that static analysis misses is served by the Visual QA Agent, which runs the actual application in a headless browser and tests every route, form, and admin action with screenshot evidence.
Emotional Jobs
Beyond functional requirements, the platform addresses several critical emotional jobs that significantly impact engineer morale, team velocity, and organizational trust in their tooling. Engineers feel profound anxiety when deploying code they cannot fully verify, knowing that a single missed defect could cause a production incident affecting thousands of users. They experience frustration when code review feedback is subjective, inconsistent between reviewers, or based on stylistic preferences rather than substantive correctness. They feel demoralization when the same class of bug recurs despite their best efforts to fix it, suggesting that their work is not producing lasting improvements. The platform directly reduces deployment anxiety by providing a quantitative Production Readiness Score that objectively measures how many critical and high-severity findings have been verified as resolved, giving engineers a concrete metric they can point to when discussing deployment readiness with stakeholders. It eliminates review frustration by replacing subjective opinions with evidence-backed findings that include exact file paths, line numbers, and quoted code snippets from the actual source. It prevents recurrence demoralization through the continuous re-audit loop that detects when a previously resolved finding has reappeared, automatically creating a regression-flagged task. The transparent, real-time dashboard gives engineers a visible sense of progress and control.

Core Features
Multi-Agent Orchestration
The platform's orchestration layer is built on a Coordinator Agent implemented as a Cloudflare Durable Object using the Think base class from the Agents SDK. The Coordinator never performs analysis itself; its sole responsibilities are spawning specialist sub-agents via typed RPC, tracking agent status (idle, running, blocked, done) in the D1 Agent Registry, managing the file claim system, and triggering the Priority Resolver Workflow once all agents have filed their initial findings. The 15 specialist sub-agents are: Architecture Agent, Security Agent, API Agent, Database Agent, Performance Agent, Testing Agent, Frontend Agent, DevOps/Infra Agent, Code Quality Agent, Error Handling Agent, Configuration Agent, Documentation Agent, Dependency Agent, Refactoring Agent, and Visual QA Agent. Each agent is a Think sub-agent with its own SQLite storage, lifecycle, and typed RPC interface. The Coordinator decides which agents to spawn based on what it detects in the repository manifest: if there is no contracts/ directory, the Smart Contract Agent is skipped; if no __tests__ directory exists, the Testing Agent is pre-loaded with a 'no tests found' finding. Each agent operates independently through a ReAct loop: it claims a file chunk from its domain queue, reads it, sends it with a structured audit prompt to the LLM via AI Gateway, parses the response into structured findings, writes each finding to the D1 findings table, and broadcasts a finding.created event that updates the dashboard in real time via WebSocket.
Cross-agent awareness is achieved through a shared database pattern rather than direct messaging. Every 30 seconds, each agent reads the findings table filtered to other agents' work and adjusts its own analysis accordingly. For example, when the Security Agent finds hardcoded secrets, the API Agent reads that finding on its next cycle and automatically escalates its audit of every endpoint where those credentials might be transmitted. The Database Agent detects missing indexes; the Performance Agent reads that finding and raises its own latency findings to higher severity. This shared-database approach prevents race conditions and circular dependencies that would arise from direct agent-to-agent RPC calls. File claims are managed through a D1 claims table with columns for agent_id, file_path, audit_run_id, and claimed_at. Before any agent reads a file, it writes a claim row. Any other agent attempting to claim the same file sees the existing claim and skips it, ensuring no two agents ever analyze the same file in the same audit run.
Anti-Hallucination Engine
The Anti-Hallucination Engine represents the platform's most critical technical differentiator and operates through three complementary enforcement layers that work in concert to prevent fabricated or unsupported claims from ever reaching the developer's task board. Layer 1, Constitutional Rules, provides each specialist agent with a CONSTITUTION.md file that is hard-injected as a pre-prompt before every single analysis turn, ensuring it cannot be bypassed or overridden by subsequent context. This constitution defines precisely what the agent is allowed to claim, the exact evidence format it must use including the required fields of file path, line range, and quoted snippet, a list of banned phrases that indicate unverified optimism such as 'production ready,' 'looks good,' 'should work,' and 'probably fine,' and the mandatory requirement to explicitly label any unknown as unknown rather than inferring an answer based on pattern recognition. The constitution is structurally injected before every LLM API call and cannot be overridden by user messages, system prompts from other agents, or accumulated conversation context.
Layer 2, Verification Gates, operates between the agent's LLM output and the D1 findings table. No finding can be written to the database without passing through a deterministic schema validation check implemented as plain TypeScript code, not as an LLM evaluation. The gate validates that all required fields are present (evidence_quote, file, line_range, severity, category, description, impact), that severity marked as 'critical' includes an impact field, that no banned phrases appear in the description, and that the file path in the finding actually exists in the repository manifest. If the gate rejects the output, the agent must retry its analysis with the rejection reason included in its context, preventing sycophantic or shallow responses from ever reaching the task board. Layer 3, Behavioral Tuning, exposes a set of configurable dials on the dashboard per agent: audit aggressiveness, evidence strictness level, maximum retry attempts before triggering the Salvation Protocol, whether the agent is allowed to suggest fixes or only report findings, and whether cross-agent findings should escalate or stay isolated. These settings are stored in D1 and injected into every agent's context, allowing tenants to customize audit behavior without code changes.
Salvation Protocol
The Salvation Protocol is a structured escalation mechanism that prevents agents from silently failing on intractable findings or entering infinite retry loops. When a specialist agent fails to resolve a finding through three consecutive attempts (tracked per finding via an attempt counter in D1), it automatically transitions from analysis mode into Research Phase. During this phase, the agent constructs structured search queries based on the finding's category and severity, targeting authoritative external sources: OWASP documentation for security issues, the National Vulnerability Database (NVD) for CVE references, the relevant framework's GitHub Issues for known runtime errors, and Stack Overflow for implementation patterns and accepted workarounds. The agent reads the top results from each source and extracts four categories of information: known solutions that have been validated by the community, accepted workarounds that reduce but do not eliminate the issue, whether this is a recognized unsolvable class of problem (such as a fundamental framework limitation), and an estimated human effort required to implement the recommended approach. Critically, all sources must include direct URLs; the agent is constitutionally prohibited from inventing references.
After completing the Research Phase, the agent files a Salvation Report, which is a structured D1 record (not a chat message or free-text blob) containing every attempt log with timestamps and outcomes, every research source with a URL, title, and relevant snippet, a human-readable recommendation that classifies the next step as one of four options: hire a specialist, file a vendor bug report, require architectural redesign, or implement a specific documented workaround. The report also includes a list of task IDs that are now blocked by this unresolvable finding, enabling the Coordinator to immediately notify all other agents. Dependent tasks do not get silently stalled; they are re-ranked with an explicit 'blocked by Salvation Report #X' tag that is visible on the dashboard and in every agent's shared knowledge read cycle. This ensures that human developers are always aware of blocking issues and can make informed decisions about resource allocation.
Visual QA Agent
The Visual QA Agent is a specialist sub-agent that operates fundamentally differently from all other agents in the system. While every other agent performs static analysis by reading source code, the Visual QA Agent runs the actual deployed application in a headless Chromium browser instance via Cloudflare Browser Run. This catches an entirely different and complementary class of defects that static analysis cannot detect: a button that exists in the DOM but fires no click handler, a form that renders correctly but silently fails to submit data, an admin route that returns HTTP 200 but renders a blank panel, or a settings page that loads successfully but fails to persist changes to the backend. Static analysis sees the handler function exists and marks it as fine; the Visual QA Agent actually clicks the button, monitors the network tab, observes zero requests fired, and files a high-severity finding with screenshot evidence.
For each feature under test, the Visual QA Agent generates a test script from the route map and any existing API documentation. The test script defines the exact sequence of actions (navigate to URL, click element, fill form field, submit), records every network request with status code, captures the DOM state after each action, takes a screenshot at the critical assertion point, and produces a structured pass/fail/warn verdict with full evidence. Admin features receive an elevated test pass: the agent logs in with an admin user account and re-runs every action exposed by admin-only routes, including every settings panel, every management action, and every role-restricted button. Any admin action that fires no request, returns a non-200 status code, or leaves the UI in a stale state triggers an automatic high-severity task that is injected directly into the priority queue alongside static analysis tasks, tagged with source: visual_qa so developers immediately know these are runtime-verified failures rather than statically inferred issues.
Real-Time Dashboard
The dashboard serves as the central control room for the entire audit lifecycle, providing real-time visibility into agent activity, findings, task progress, and system health. It is built as a Next.js frontend deployed on Cloudflare Pages, communicating with the backend exclusively through WebSockets provided by Durable Objects. The primary view is a Kanban task board with four columns: Pending, In Progress, In Review, and Done. Each task card displays the file path, severity badge, domain tag, estimated effort, and a one-line summary of the finding. Clicking a card opens a detail pane showing the full finding: the exact evidence quote with line numbers, the impact description, the suggested fix approach, the agent that filed it, and the complete history of verification attempts. When a developer moves a card to In Progress, the corresponding file is locked in the claims table, preventing any agent from re-auditing it while human work is underway. The lock includes an auto-expiry timer (48 hours) to prevent permanent blocking if a developer goes unavailable.
Beyond the task board, the dashboard provides four additional panels. The Agent Activity panel shows a real-time log stream of every agent's actions: which files they are claiming, which findings they are filing, and their current status. The Production Readiness panel displays the overall score as a large percentage with a trend indicator, along with a breakdown by severity level showing how many critical, high, medium, and low findings remain open versus resolved. The Cost panel shows real-time token usage broken down by agent, model (Kimi K3 versus MiniMax M3), provider, and task type, with a running total cost in USD computed from the token_usage table. The Salvation panel lists all active Salvation Reports with their blocking task lists, research sources, and recommended next steps, giving engineering managers immediate visibility into issues that require human intervention. All panels update in real time via WebSocket events emitted by Durable Objects whenever a finding is created, a task status changes, or an agent's state transitions.
Continuous Audit Lifecycle
The platform does not perform a single one-time audit and stop. Instead, it implements a continuous eight-phase lifecycle that runs until every critical and high-severity finding has been verified as resolved. Phase 0 is Repository Ingestion: a human developer submits a repository via zip upload or GitHub URL, and the Ingestion Worker walks every file, builds a flat manifest (path, size, language, last modified), chunks each file into segments of 500 lines or fewer, stores chunks in R2, tags each chunk with its detected domain (frontend, backend, config, test, infra), and emits a repo.ready event. Phase 1 is Coordinator Boot: the Coordinator reads the manifest, decides which specialist agents to spawn based on detected file types, writes an Agent Registry to D1, sets the global audit_run_id, and emits spawn commands. Phase 2 is Parallel Domain Audits: each specialist agent claims file chunks from its domain queue, reads them, analyzes them through the ReAct loop, and writes structured findings to D1. Phase 3 is Cross-Agent Awareness: agents periodically read other agents' findings and adjust their own analysis.
Phase 4 is Priority Resolution: a Cloudflare Workflow (not an agent) loads all findings and computes a composite priority score using deterministic math. The formula uses a base score from severity (critical equals 100, high equals 75, medium equals 40, low equals 15, info equals 5), applies a 1.5x multiplier if multiple agents flagged the same file, a 1.3x multiplier if the finding blocks another finding from being fixable, a 1.2x multiplier if the finding is in a file with zero test coverage, and a 0.8x discount if the file is already claimed for refactoring. Findings are grouped into tasks with estimated effort, blocking relationships, and assigned domains. Phase 5 is Developer Execution: developers pick tasks from the priority queue, implement fixes locally, and push commits. Phase 6 is Verification: the Verification Agent fetches the commit diff, re-reads changed files, and determines whether the original evidence is still present, marking the task as Done, Needs Revision, or Failed Verification. Phase 7 is Continuous Re-Audit: the Coordinator polls for commit changes every hour, re-queues modified files for their domain agents, diffs new findings against existing ones, and handles recurrence counting, auto-closing, and regression detection.
Multi-Tenant Isolation
The platform is architected as a multi-tenant SaaS product from day one, with data isolation designed into every layer of the system rather than bolted on as an afterthought during a future scaling phase. Every D1 table includes a mandatory tenant_id column as its first column, and every database query without exception filters by tenant_id as a mandatory WHERE clause condition. This applies uniformly to the repo_manifest, file_chunks, claims, findings, tasks, agent_registry, token_usage, salvation_reports, knowledge_ledger, and all other tables in the schema. The tenant_id value is extracted from the authenticated user's session at the API gateway layer and passed through the entire request chain as an immutable context value that cannot be modified by any downstream component. No agent, no Worker, and no API endpoint can access data belonging to a different tenant, even if a malicious or buggy client manually specifies a different tenant_id in a request, because the gateway layer unconditionally overwrites any client-provided tenant_id with the authenticated value derived from the user's session token. This dual-layer approach prevents both accidental cross-tenant data leakage and deliberate cross-tenant access attempts.
Secrets discovered during audits receive an additional layer of protection. When any agent identifies a potential secret (API key, OAuth token, database password, private key), the raw value is never written to the findings table in plaintext. Instead, the secrets redaction layer computes a SHA-256 hash of the value and stores only the hash in the evidence_quote field, replacing the raw secret with a placeholder like [REDACTED:sha256:a1b2c3...]. The dashboard displays only the hash and the file path where the secret was found, never the actual value. This ensures that the findings database itself does not become a secrets repository that could be compromised in a data breach. The raw secret value exists only transiently in the agent's memory during the single LLM call that detected it and is never persisted to any storage layer. R2 object storage keys are also namespaced by tenant_id, and each tenant's file chunks are stored in a separate R2 prefix, providing storage-level isolation in addition to database-level isolation.
Production Readiness Score
The Production Readiness Score provides a single, quantitative metric that communicates the overall health and deployment readiness of a repository at a glance, serving as the primary headline number on the dashboard. It is calculated as a percentage using the formula: Production Readiness Score equals (verified_resolved divided by total_critical_and_high) multiplied by 100. This formula intentionally counts only critical and high-severity findings in the denominator, ensuring that the score reflects the issues that truly matter for production deployment rather than being diluted by hundreds of low-severity style violations or informational findings. For example, a repository with 20 critical and high-severity findings, of which 18 have been independently verified as resolved by the Verification Agent, scores 90 percent. The score is recalculated deterministically after every verification cycle, meaning it updates in real time on the dashboard as developers close tasks and the Verification Agent confirms each fix. It is stored as a single record in D1 with columns for tenant_id, repo_id, audit_run_id, score_value, critical_total, critical_resolved, high_total, high_resolved, and last_updated timestamp, providing a complete audit trail of score changes.
The score is designed to be action-oriented rather than merely informational. A score below 50% triggers a visual warning on the dashboard and a recommendation to pause non-essential feature work until the score improves. A score above 90% indicates that the repository is approaching production readiness, though the system never labels any codebase as definitively 'production ready' (this phrase is banned by the Constitutional Rules). The score also serves as a trend indicator: the dashboard displays the score history over time, allowing engineering managers to see whether their team's velocity of issue resolution is accelerating or decelerating. The score is computed deterministically from D1 data; no LLM is involved in its calculation, ensuring it is reproducible and auditable. It is exposed via the API so that external systems (CI/CD pipelines, executive dashboards, compliance tools) can consume it programmatically and set automated policies such as blocking deployment when the score falls below a configured threshold.
Non-Functional Requirements
Performance
The platform must operate within Cloudflare Workers' execution constraints while delivering a responsive user experience. Each Worker invocation is limited to 128 MB of memory and a configurable CPU time limit (default 30 seconds on paid plans, extensible to 5 minutes via the limits.cpu_ms Wrangler configuration). The architecture is designed so that LLM inference time, which is I/O-bound while waiting for the API response, does not count against CPU limits. The default subrequest limit of 10 per Worker invocation is handled through careful fan-out design using Cloudflare Queues for parallel agent spawning rather than direct chained RPC calls. The dashboard must achieve sub-100ms WebSocket latency from finding creation to UI update, measured via the browser Performance API. Repository ingestion must complete within 60 seconds for repos under 10,000 files. The system must support at least 10 concurrent audit runs per tenant without degradation, leveraging Durable Object hibernation (agents wake on demand and cost nothing when idle) and horizontal scaling across Cloudflare's global edge network. Token budget enforcement per agent prevents context ballooning: each agent has a configurable maximum token count per analysis turn, with automatic context compression when approaching the limit.
Security
Security requirements address both the platform's own security posture and the security of the repositories it audits. Multi-tenant isolation is enforced at every layer: database queries filter by tenant_id, R2 storage is namespaced by tenant prefix, and the API gateway overwrites any client-provided tenant_id with the authenticated value. Authentication is required for all dashboard and API access; the dashboard must not be publicly accessible, as it displays sensitive information including architecture maps, security findings, and (redacted) secrets. Discovered secrets are SHA-256 hashed before storage and never written to any persistent layer in plaintext. All LLM API calls are routed through Cloudflare AI Gateway, which provides unified inference with support for 14+ model providers and prevents direct model endpoint exposure. The dual-model routing strategy (Kimi K3 for deep reasoning, MiniMax M3 for high-frequency tasks) is implemented through a single modelRouter() function that every agent calls, ensuring consistent cost tracking and preventing unauthorized model access. Rate limiting is enforced per tenant to prevent a single large repository audit from consuming the entire API budget; when rate limits are hit, agents are queued with exponential backoff rather than failing silently.
Reliability
The platform must maintain audit state integrity across Durable Object restarts, which occur transparently when Cloudflare recycles isolates. The critical reliability mechanism is the D1 claims table: because every agent's file claim is persisted to D1 (not held in memory), a restarted agent can resume exactly where it left off by querying its existing claims and identifying the next unclaimed file in its domain queue. Each agent maintains a resumable cursor stored in D1 on every file processed, ensuring that cold-start recovery does not re-analyze already-processed files or skip unprocessed ones. Cloudflare Workflows provide durable execution for the Priority Resolver, meaning that even if the Worker running the resolver is interrupted, the Workflow's state is preserved and execution resumes from the last checkpoint. The continuous re-audit loop is driven by scheduled checks rather than in-memory timers, ensuring it survives restarts. The Salvation Protocol's structured D1 records ensure that research results are never lost even if the agent that performed the research is terminated mid-execution.
Scalability
The platform's architecture is inherently horizontal and scales with Cloudflare's global edge network. Durable Objects support millions of instances, one per tenant or audit session, each costing nothing when idle due to automatic hibernation. The file-claim system in D1 provides natural load balancing: agents claim files independently and in parallel, with no central bottleneck coordinating access. Cloudflare Queues handle the fan-out of agent spawn commands, supporting at least 15 concurrent agents per audit run with additional capacity for verification agents spawned on demand. The system must support at least 100 concurrent tenants, each running independent audits, without cross-tenant interference. Storage scales independently: R2 provides unlimited object storage for file chunks, and D1 supports databases up to 10 GB per instance (sufficient for hundreds of thousands of findings per tenant). The token usage tracking system must handle at least 10,000 API call records per day per tenant without query performance degradation, addressed through appropriate D1 indexing on the token_usage table's tenant_id and timestamp columns. Git diff ingestion via GitHub API, with planned adapters for GitLab, Bitbucket, and self-hosted Gitea, ensures the platform scales to support any source control provider.
Out of Scope
The following items are explicitly out of scope for the initial release of the platform and are documented here in detail to set clear expectations with stakeholders, prevent scope creep during development, and provide a transparent roadmap for future engineering investment. These items represent recognized gaps in the current architectural plan that have been identified through honest self-assessment and are acknowledged but deliberately deferred to future phases based on their implementation complexity, their dependence on external integrations, and the platform's core value proposition of delivering anti-hallucination multi-agent code auditing. Each out-of-scope item includes a detailed explanation of why it is deferred, what specific risks its absence introduces for production users, would be required to bring it fully into scope in a subsequent release. These gaps have been identified through rigorous architectural review and represent an honest, transparent acknowledgment of the significant engineering work that remains beyond the core platform's auditing capabilities.
Git Diff Ingestion Pipeline
The current architecture assumes that repository files already exist in R2 storage but does not define the complete ingestion pipeline for connecting to source control providers and keeping the stored files in sync with the live repository. A production-grade implementation requires several missing components: GitHub webhook integration to receive push events and trigger re-audits automatically, OAuth authorization flows to authenticate with source control providers on behalf of the tenant user, zip upload handling with virus scanning for repositories submitted without a remote URL, and delta sync mechanisms that update only changed files when new commits are pushed rather than re-ingesting the entire repository from scratch. Additionally, while the Verification Agent reads diffs via the GitHub API, broader support for GitLab, Bitbucket, and self-hosted Gitea requires adapter implementations for each provider's diff and webhook APIs. This is the first engineering work item that would block production deployment and is planned as the top priority for Phase 2.
Agent Cold-Start Recovery
While the D1 claims table ensures that file claims survive Durable Object restarts, the agent's in-memory state (its position in the analysis queue, cached context from cross-agent reads, and partial LLM conversation history) is lost when Cloudflare recycles the isolate, which happens transparently and without warning as part of normal platform operations. A production system requires a resumable cursor per agent stored in D1 on every file processed, ensuring that upon restart the agent can query its cursor and resume from exactly where it left off without re-analyzing already-processed files or skipping files that were queued but not yet analyzed. Additionally, a context hydration step must rebuild the agent's working memory from the knowledge ledger before resuming analysis, restoring awareness of cross-agent findings that informed its previous analysis decisions, and preventing the agent from wastefully re-discovering issues that were already identified and filed in the previous session, which would create duplicate findings and confuse the priority ranking.
Environment Simulation for Visual QA
The Visual QA Agent requires a running instance of the application under test to perform its core function of runtime verification through headless browser interaction. This includes a staging URL that points to a deployed version of the application, seeded test data that populates the database with known fixtures for form submissions and list views, and environment configuration including API keys, database connections, and feature flags. The current plan does not define how staging environments are provisioned (whether through cloud provider APIs, container orchestration, or serverless preview deployments), how test data is generated and maintained across audit cycles to ensure consistent and repeatable test conditions, or how the staging environment is kept in sync with the specific commit being audited rather than drifting out of alignment as the repository evolves. Without this supporting infrastructure, the Visual QA Agent cannot perform its core function and would be testing against a blank or stale application instance, producing either false positives from broken staging environments or false negatives from environments that do not reflect the actual code.
Multi-Repository Support
The current D1 schemas and agent coordination logic assume a single repository per audit run, with all tables keyed by a single repo_id that maps to exactly one repository at a time. Supporting monorepos that contain multiple independently deployable microservices, microservice architectures that span multiple repositories with shared dependencies, and cross-repo dependency analysis that comprehensively traces a function call from a frontend repo through a shared library repo to a backend API repo requires several non-trivial database schema extensions (including a new repo_group concept), significant agent coordination changes to handle inter-repo file claims, and a unified dependency graph that spans repository boundaries and can track cross-repo impact chains end-to-end. This level of sophistication is deliberately deferred to a future phase once single-repo auditing has been proven and is demonstrably stable in production, ensuring that the foundation is solid and battle-tested before adding the additional complexity of cross-repo coordination and dependency tracking.
Token Budget Enforcement
While the dual-model routing strategy reduces overall cost by routing tasks to the most cost-effective model based on task type and estimated token count, there is currently no per-agent token budget cap that prevents an agent from repeatedly reading the same large files and inflating its context window beyond what is necessary for the analysis. An agent that reads a 500-line file chunk, then re-reads it on its next turn because it forgot the content, then reads it a third time during cross-agent awareness checking could consume three times the necessary tokens without any mechanism stopping it. Future work includes configurable per-agent token budgets enforced by a middleware layer, automatic context compression using summarization before expensive model calls, and proactive warnings when an agent approaches the model's maximum context window limit so that the Coordinator can intervene before the call fails, potentially saving the agent's progress and preventing wasted tokens on calls that would be truncated or rejected by the model provider.
Secrets Redaction Enhancement
The current SHA-256 hashing approach effectively prevents raw secrets from being persisted to any storage layer, but the pattern-matching logic that identifies which values in the source code are actually secrets (versus normal string literals, configuration values, or test fixtures) is imperfect and may produce false positives on benign strings or miss custom secret formats used by specific frameworks or organizations. A future enhancement would integrate with dedicated secrets detection services such as GitGuardian or TruffleHog, which maintain comprehensive databases of known secret patterns, entropy-based detection algorithms, and allowlist support for known non-secret values. This integration would provide more accurate identification and classification of sensitive values across the diverse range of secret formats found in modern applications, from API keys and JWT tokens to database connection strings and cloud provider credentials, ensuring that the platform's security posture extends beyond simple hashing to truly comprehensive secret lifecycle management across all stages of the audit pipeline.
Rate Limiting and Backpressure
The Coordinator can spawn up to 15 agents simultaneously, each making rapid sequential API calls to the LLM provider through the AI Gateway. In the current design, there is no per-minute call budget enforced at the platform level, no backpressure mechanism that detects when the upstream provider is rate-limiting the platform's requests, and no durable retry queue for API calls that fail due to rate limits or transient network errors. A single large repository audit with 15 active agents could exhaust the provider's rate limits within minutes, causing cascading failures across all agents. Future work includes implementing a token bucket rate limiter per tenant that distributes API capacity fairly across concurrent audits, an exponential backoff retry queue backed by Cloudflare Queues that durably stores failed API calls for automatic retry, and circuit breaker logic that pauses agent spawning when the sustained error rate exceeds a configurable threshold, preventing the system from entering a thundering herd failure mode during peak usage periods.
